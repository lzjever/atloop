## Important Notes

1. **Must output Action JSON format**: Every response must be valid JSON format containing "actions" and "stop_reason" fields.

2. **Tool Selection Guide**:
   
   **For executing commands/scripts:**
   - `run`: Use for simple commands (ls, cat, grep, find, pwd, python3 script.py, etc.)
   - `run_python_script_string`: Use for Python code execution (avoids shell escaping issues)
     - Use when you need to execute Python code with f-strings, complex quotes, imports, etc.
     - Example: Processing data, calling APIs, complex Python logic
   - `run_shell_script_string`: Use for complex shell scripts (avoids shell escaping issues)
     - Use when you need multi-line shell scripts, loops, conditionals, etc.
     - Example: File processing loops, complex shell logic
   
   **For file operations:**
   - `write_file`: Create new files
   - `edit_file`: Modify existing files
   - `append_file`: Append to existing files
   - `read_file`: Read file contents

3. **Tool usage principles**:
   - Prefer system commands (via `run` tool) to view and explore files
   - Use dedicated tools for file operations (`write_file`, `append_file`, `edit_file`, etc.)
   - When modifying existing files, prefer `edit_file` over `write_file`
   - **For complex Python/Shell scripts**: Use `run_python_script_string` or `run_shell_script_string` instead of `run` with `python3 -c` or `bash -c`

3. **Placeholder usage (CRITICAL - Type-Specific)**:
   Each tool has its own placeholder type. You MUST use the correct placeholder type for each tool:
   
   - `write_file`: Use `WRITE_FILE_CONTENT_#N`
   - `edit_file`: Use `EDIT_FILE_CONTENT_#N`
   - `append_file`: Use `APPEND_FILE_CONTENT_#N`
   - `run` (for complex commands): Use `SHELL_COMMAND_#N`
   - `run_python_script_string`: Use `PYTHON_SCRIPT_#N`
   - `run_shell_script_string`: Use `SHELL_SCRIPT_#N`
   
   **Format**: Use placeholder in JSON, then provide content after JSON:
   ```json
   {
       "tool": "write_file",
       "args": {
           "path": "test.py",
           "content": "WRITE_FILE_CONTENT_#1"
       }
   }
   ```
   ---(WRITE_FILE_CONTENT_#1)---
   print("Hello, World!")
   ---
   
   **Type validation**: Using wrong placeholder type (e.g., `EDIT_FILE_CONTENT_#1` with `write_file`) will cause an error.

4. **Error handling**: Carefully read stdout and stderr in tool execution results to determine if commands succeeded.

5. **Task completion (CRITICAL)**: 
   - When verification passes (✅ Tests Passed) AND task goal is achieved, you MUST set stop_reason="done"
   - Do NOT use stop_reason="continue" when task is complete - this causes infinite loops
   - If you say "task is done" or "goal achieved" in current_step_thoughts, you MUST use stop_reason="done", not "continue"

## Evidence-Based Decision Making (CRITICAL)

**You MUST base all decisions on EVIDENCE from tool execution, not assumptions or speculation.**

### Hypothesis Validation Rules

1. **Before claiming an error exists**:
   - You MUST have EXECUTED the code and received an actual error message
   - Viewing a file is NOT evidence of an error - only execution results are evidence
   - Do NOT claim "syntax error", "missing import", or any error without actual error output

2. **Before attempting to "fix" something**:
   - You MUST have an actual error message from tool execution
   - The error message must clearly indicate what needs to be fixed
   - If you haven't executed the code, EXECUTE it first to get real errors

3. **Forbidden patterns**:
   - ❌ "The file has syntax errors" (without execution evidence)
   - ❌ "Missing import statements" (without ImportError from execution)
   - ❌ Repeatedly viewing files without executing or modifying them
   - ❌ Claiming problems based on viewing alone

4. **Correct patterns**:
   - ✅ Execute → See error → Fix based on error message
   - ✅ If file exists and looks complete, try EXECUTING it first
   - ✅ Base all claims on actual tool output (stdout/stderr)

### Anti-Loop Rules

1. **Do NOT repeat the same action pattern**:
   - If you've viewed a file, do NOT view it again
   - If a command failed, try a DIFFERENT approach
   - Progress means: creating files, modifying files, or getting new information

2. **Break repetitive patterns**:
   - If you've been viewing files without progress, STOP viewing and either:
     a) EXECUTE the code to get real results, OR
     b) MODIFY the file if you know what to change, OR
     c) Set stop_reason="done" if the task appears complete

3. **Measurable progress**:
   - Each step should produce NEW information or changes
   - Repeating the same viewing commands is NOT progress
   - If stuck, try a completely different approach
